# Agent 选择、workflow 与交付稳定性

[English](architecture.md) · [函数级实现](implementation.md) · [测试索引](../TESTING.md)

系统每次只处理一个输入事件：保存、推进案件、保存回复，然后停止。下一封邮件继续原案。等待客户准备材料时，不持续运行模型。

## 为什么选这些组件

| 层 | 实现 | 取舍 |
|---|---|---|
| 模型运行时 | PydanticAI 的 `Proposal` / `Guidance` | 结构化输出、工具循环、可替换测试模型 |
| 材料读取 | pypdf、PDFium、RapidOCR、原图/渲染页 | 可以逐页检查 OCR 与图像 |
| 业务 workflow | `service.py`、`rules.py`、`evidence.py` 直接函数调用 | 状态和判断能直接读懂，不额外造工作流框架 |
| 状态 | SQLite 事务、唯一约束、SHA-256 文件 | 简单实现恢复与去重，接受低吞吐限制 |
| 邮箱 | 标准库 IMAP/MIME/SMTP，业务路由和 outbox 自写 | 复用成熟协议库，案件规则由应用负责 |
| 后续渠道 | Chatwoot 接口边界，尚未落地 | 复用收件工作台，无需 fork 大型 Rails/Vue 项目 |

Camunda KYC 参考异步补件，DocProof 参考提取与检查分层，LangChain 邮件示例参考评测与人工接管。这些是设计来源，不是已集成的业务引擎。当前没有一套现成签证框架替本项目完成全部业务。[复用声明](../THIRD_PARTY_NOTICES.md)。

## 一封邮件怎么运行

1. `QQInbox.poll()` 只读收件箱，保存账号/UIDVALIDITY/UID 游标；Message-ID 和内容哈希识别投递。
2. `QQInbox.receive()` 解析引用链，`Inbox._receive()` 绑定渠道、账号、线程、发件人与 Case；客户不能指定其他人的 case ID。
3. `VisaService.handle_event()` 保存事件、使旧批准失效，再读取附件、让模型提出候选事实。来源是消息或具体文件页。
4. `apply_proposal()` 核对来源归属、原文和值格式；冲突保留双方，邮件自述不能代替需要文件的证据。
5. `rules.evaluate()` 计算适用性和缺项，之后 `guidance.guide()` 从真实未解决检查项选择最多三个问题。
6. 保存状态、事实、检查、回复和 trace。完成后 `build_pack()` / `verify_pack()` 核对导出，`send_prepared_reply()` 再检查当前案件和规则版本后发送。

当前 SQLite 写事务包含模型调用，所有案串行。这使恢复语义易读，但不支持高吞吐。扩容应先拆成持久任务和按案租约；增加多 Agent 不能自动解决这一瓶颈。

## 业务不确定性如何处理

| 不确定的内容 | 处理 |
|---|---|
| 路线或适用条件未知 | 询问缺失条件，不能当作“不适用” |
| 未实现的政策/业务分支 | `NEEDS_HUMAN`，不猜测通过 |
| OCR、缺页、读取容量不足 | 写明读取问题，不能静默算作有效证据 |
| 候选字段没有可靠原文 | 拒绝或保留待确认，不静默写入 |
| 两份材料冲突 | 保留双方来源及阻塞项 |
| 文件真伪 | 超出自动检查范围，不能声称已鉴定 |
| SMTP 超时但可能已送达 | `uncertain`，人工核对后再决定重发 |

曾出现自写字段 PDF 被误判完整的真实失败，已复现修复，保留在[材料质量报告](document-quality.md)。原文可定位只能证明出处，不能证明每个自然语言句子的语义都被正确理解。

## 状态与开关

| 状态 | 含义 |
|---|---|
| `WAIT_USER` | 需要回答、补件或清晰文件 |
| `NEEDS_HUMAN` | 未支持分支、冲突或需要专业判断 |
| `BLOCKED` | 处理、模型或校验失败，需要诊断 |
| `READY_FOR_REVIEW` | 当前清单满足，且启用了 HITL |
| `COMPLETE` | 按当前部署审核策略完成材料收集 |

HITL 和样例模式独立，创建案件时绑定。HITL 开启时，独立入口批准当前版本和证据清单；关闭时应用记录“自动按清单完成”，不生成虚假的人工批准。材料或规则变化使旧结论失效。样例模式允许带标记的合成证据参与演示，缺项、冲突、文件不可读仍会阻止完成。

## 上下文与停止点

每轮放入服务职责、路线 SOP、结构化事实/检查、新输入与材料摘录，以及最近最多 20 轮完整对话。工作区预算 32,000 字符：先缩短摘录，再移除旧对话；核心内容仍超限则停止。完整消息和文件保留本地。这个字符上限不等于服务商最终请求的 token 上限。

工具只允许读取当前案件已有材料。重复无进展读取停止；提取、工具、引导和重试共用每事件四次 HTTP 请求，瞬时错误最多重试一次，SDK 隐藏重试关闭。累计用量持久记录，默认无累计上限。等待客户不调用模型。

[SOUL](../src/visa_agent/prompts/SOUL.md) 定义热情、易懂的服务原则。模型选择问题优先级，应用按事实渲染状态、进度、双语措辞和交付指引。附件中的指令不能更改系统职责或增加工具权限。

## 调试路径

按“原文 → 候选字段 → 已采纳/待确认事实 → 规则结果 → 状态 → 回复 → 邮件回执”阅读 trace。日志包含模型、提示词、规则版本、用量和 run ID。原始客户 trace 不公开发布。[部署排查](deployment.zh-CN.md#排查和升级)。
